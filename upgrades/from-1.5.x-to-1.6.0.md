# From 1.5.x to 1.6.0

This page describes the changes you need to make when upgrading from version 1.5.x to 1.6.0.

{% hint style="success" %}
**Nothing is removed in 1.6.0.** Everything below keeps working exactly as before. The release
exists to give you a full minor version to migrate before 2.0.0 takes the deprecated pieces away.
{% endhint %}

## The bundle is narrowing its scope

The bundle is going back to what it does well: the **web manifest**, the **service worker**, and
the **favicons, icons and screenshots**. Everything on the client-integration side is leaving.

Two things drove the decision. Wrapping a browser API in a generic, configurable Stimulus
controller turns out to be a lot of abstraction for very little reuse: every project wants its own
behaviour, its own UI and its own error handling. And several of those controllers push real-time,
client-side interactions through the server and back, a round trip that is rarely what an
application actually wants.

The full rationale is in
[this comment](https://github.com/Spomky-Labs/pwa-bundle/issues/372#issuecomment-5295710299).

## Deprecated: the Stimulus controllers

All 27 controllers shipped by the bundle are deprecated and will be removed in 2.0.0, along with
the `@spomky-labs/pwa-bundle` npm package.

Each one prints a warning in the browser console the first time it is mounted:

```
[pwa-bundle] The "pwa--web-push" Stimulus controller is deprecated since 1.6.0 and will be
removed in 2.0.0. Copy the controller into your own application and register it there.
```

**What to do:** copy the controllers you actually use into your own application and register them
there. They are plain Stimulus controllers with no dependency on the bundle, so nothing is lost in
the move, and you get to drop the parts you never needed.

```bash
# for instance
cp vendor/spomky-labs/pwa-bundle/assets/src/geolocation_controller.js assets/controllers/
```

The two page-side helpers exported through `@spomky-labs/pwa/helpers`, `onPeriodicSync()` and
`registerPeriodicSync()`, are deprecated too. `registerPeriodicSync()` is a handful of lines you
can inline:

{% code title="assets/app.js" lineNumbers="true" %}
```javascript
const registration = await navigator.serviceWorker.ready;
const status = await navigator.permissions.query({ name: 'periodic-background-sync' });

if (status.state === 'granted' && 'periodicSync' in registration) {
    const tags = await registration.periodicSync.getTags();
    if (!tags.includes('my-tag')) {
        await registration.periodicSync.register('my-tag', { minInterval: 24 * 60 * 60 * 1000 });
    }
}
```
{% endcode %}

## Deprecated: part of the service worker helpers

The service worker generated by the bundle used to declare a number of helper functions. Most of
them wrap events **the bundle itself never handles**: `push`, `notificationclick`, `message`,
`periodicsync` and the three `backgroundfetch` events have no producer on the PHP side.

Service worker listeners are additive, and your own source file (the `src` option) is appended
last, so a plain `self.addEventListener()` there does exactly the same job without the
indirection.

The following helpers are deprecated:

| Helper | Replacement |
|--------|-------------|
| `registerCacheFirst()` | Build the strategy and call `workbox.routing.registerRoute()` directly |
| `registerMessageTask()` | `self.addEventListener('message', ...)` |
| `registerPushTask()` | `self.addEventListener('push', ...)` |
| `registerNotificationAction()` | `self.addEventListener('notificationclick', ...)` |
| `registerPeriodicSyncTask()` | `self.addEventListener('periodicsync', ...)` |
| `registerBackgroundFetchTask()` | `self.addEventListener('backgroundfetchsuccess', ...)` and its siblings |
| `openBackgroundFetchDatabase()` | Open your own database |
| `structuredPushNotificationSupport()` | Parse the payload and call `showNotification()` yourself |
| `simplePushNotificationSupport()` | Same |
| `notifyPeriodicSyncClients()` | Create your own `BroadcastChannel` and post to it |

Each of them warns in the console **when it is actually called**, so an application that already
stopped using them gets a silent service worker.

### What stays

These are not going anywhere, because your own source file cannot replace them: they either
arbitrate an order between the rules the bundle generates, or carry a state shared with them.

- `registerInstallTask()` and `precacheResources()`
- `registerCacheName()`, `openCache()` and the new `registerClearCacheListener()`
- `statusGuard()`, `createBackgroundSyncPlugin()` and `createBackgroundSyncPluginWithBroadcast()`
- the `SKIP_WAITING` message handler, which is the service worker half of the update flow

### Migrating

Replace the calls in your own service worker source:

{% code title="assets/sw.js" lineNumbers="true" %}
```javascript
// registerPushTask(structuredPushNotificationSupport);
self.addEventListener('push', (event) => {
    const { title, options } = JSON.parse(event.data.text());
    event.waitUntil(self.registration.showNotification(title, options));
});

// registerNotificationAction('*', handler);
self.addEventListener('notificationclick', (event) => {
    event.notification.close();
    event.waitUntil(handler(event));
});

// registerPeriodicSyncTask('my-tag', callback);
self.addEventListener('periodicsync', (event) => {
    if (event.tag === 'my-tag') {
        event.waitUntil(callback(event));
    }
});

// registerMessageTask(callback);
self.addEventListener('message', (event) => {
    event.waitUntil(callback(event));
});
```
{% endcode %}

Then turn the helpers off:

{% code title="config/packages/pwa.yaml" lineNumbers="true" %}
```yaml
pwa:
    serviceworker:
        workbox:
            keep_deprecated_helpers: false
```
{% endcode %}

As long as this option is left to `true`, the bundle triggers a deprecation notice at container
build time. Setting it to `false` is what silences it, and it is the exact change 2.0.0 will make
for you.

{% hint style="warning" %}
Setting `keep_deprecated_helpers` to `false` stops the `idb` library from being imported into the
service worker and copied to the public folder, because `openBackgroundFetchDatabase()` was its
only consumer. If your own source file uses `self.idb`, switch to `indexedDB.open()` or import the
library yourself.
{% endhint %}

## Deprecated: background fetch

The `background_fetch` option is deprecated and will be removed in 2.0.0.

It decides for you that a click opens a given URL, that downloads are chunked into a fixed
IndexedDB schema and that the notification title is rewritten with `{title} ✅`. That is a lot of
opinion for a feature every application ends up wanting differently.

{% code title="config/packages/pwa.yaml" lineNumbers="true" %}
```yaml
pwa:
    serviceworker:
        workbox:
            background_fetch:      # deprecated since 1.6.0
                enabled: true
```
{% endcode %}

Handle the events in your own source file instead. `self.idb` remains available as long as
`keep_deprecated_helpers` is `true`, and the storage is a dozen lines with plain `indexedDB`:

{% code title="assets/sw.js" lineNumbers="true" %}
```javascript
self.addEventListener('backgroundfetchsuccess', (event) => {
    event.waitUntil((async () => {
        const records = await event.registration.matchAll();
        for (const record of records) {
            const response = await record.responseReady;
            // store it the way your application needs
        }
        await event.updateUI({ title: 'Download complete' });
    })());
});
```
{% endcode %}

{% hint style="danger" %}
Enabling `background_fetch` while `keep_deprecated_helpers` is `false` now fails at container
build time with an explicit message, rather than producing a service worker that throws a
`ReferenceError` in the browser.
{% endhint %}

## New: purging your own caches

`clear_cache` only ever deleted the caches the bundle registers itself through
`registerCacheName()`. A cache your own service worker source opens with `caches.open()` survived
every install, silently.

The new `registerClearCacheListener()` closes the gap. The callback receives every cache name
currently stored and returns the ones to delete:

{% code title="assets/sw.js" lineNumbers="true" %}
```javascript
registerClearCacheListener((names) =>
    names.filter((name) => name.startsWith('my-app-') && name !== 'my-app-v3')
);
```
{% endcode %}

A callback rather than a list of names in the configuration, because the interesting cases are
dynamic: versioned caches where the current one must survive, prefixes, anything computed at
runtime.

Callbacks may be async, and one throwing is logged without stopping the others.

See [Cache Cleaning](../the-service-worker/workbox/cache-cleaning.md).

## Migration Checklist

- [ ] Copy the Stimulus controllers you use into your own application, register them there
- [ ] Drop the `@spomky-labs/pwa-bundle` npm dependency once nothing imports it
- [ ] Replace `onPeriodicSync()` and `registerPeriodicSync()` with the native calls
- [ ] Replace the deprecated service worker helpers with `self.addEventListener()` in your `src`
- [ ] Check the browser console: any remaining `[pwa-bundle]` warning points at a call you missed
- [ ] Set `keep_deprecated_helpers: false`
- [ ] If you used `self.idb` in your own source, switch to `indexedDB.open()`
- [ ] Replace `background_fetch` with your own `backgroundfetchsuccess` handler
- [ ] Declare the caches you open yourself with `registerClearCacheListener()`
- [ ] Run `php bin/console pwa:compile` and test with `APP_ENV=dev` to surface the deprecations
